# Claude Code Prompt R —— 操作事實蒐集（Recon）

> **這是一個很短的 session，在 Prompt A 之前執行。** 它的存在理由只有一個：讓後續**看不到程式碼**的測試撰寫者不會卡在「這個東西到底怎麼跑起來」這種與正確性無關的問題上。
>
> **執行位置：** repo 內，一般 checkout 即可（本 session 不修改任何程式碼）。

---

## 你的任務

產出一份 `docs/OPERATIONAL_FACTS.md`，記錄**如何操作這個系統**——啟動、連線、觀測。

**你不寫任何測試，不改任何程式碼。**

---

## 🔴 最重要的一條界線

這份文件**只能包含操作事實，不得包含語意契約**。

| ✅ 可以寫 | ❌ 絕對不可以寫 |
|---|---|
| compose 服務名稱、埠號、網路名稱 | 請求／回應 body 的欄位形狀 |
| DB 連線字串、容器名稱 | 哪些欄位是必填、合法值有哪些 |
| 環境變數名稱與預設值 | 狀態機行為、失敗如何分類 |
| 五張表的**表名與欄位名**（`\d` 輸出） | 欄位的語意、什麼時候被寫入 |
| 啟動指令、健康檢查方式 | 端點做什麼、回傳什麼 |
| API 端點的**路徑與 HTTP 方法** | 端點的請求／回應 schema |

**理由：** 後續的測試撰寫者要從 `spec/BEHAVIOR_MATRIX.md` 推導出系統**應該**怎麼表現。若這份文件告訴它系統**實際**怎麼表現，它會照抄實作，整個盲寫機制就失去意義了。

**判斷法：如果某項資訊能讓人推斷出「系統對某個輸入會回什麼」，就不要寫。** 只寫「怎麼把系統叫起來、怎麼跟它說話、怎麼看它的狀態」。

有疑慮時，**不寫，並在文件末尾的「我刻意省略的事項」列出來**。

## 文件內容

### 1. 啟動與關閉

- 從乾淨 clone 到可用 stack 的完整指令序列
- 只要 orchestrator + Postgres（不含 demo）的最小啟動方式
- 各服務名稱、容器名稱、對外埠、compose 網路名稱
- 如何確認已就緒（healthcheck 機制與判斷方式）
- 如何完全重置（含資料庫 volume）
- migration 何時套用、由誰套用

### 2. 資料庫存取

- 從**主機**連線的字串
- 從**同一 compose 網路的其他容器**連線的字串
- 五張表的表名，以及每張表的 `\d` 輸出（**只貼欄位名與型別，不要解釋任何欄位的意義**）

### 3. HTTP 表面

- 所有已註冊的路由：**HTTP method + 路徑**。就這樣，不要寫請求或回應的形狀
- 服務埠、是否需要認證

### 4. 環境變數

- 所有 orchestrator 讀取的環境變數：名稱、預設值、格式錯誤時的行為（fail-fast 或退回預設）
- 從何處讀取（compose、Dockerfile、程式碼）

### 5. 網路拓樸（**這一節最關鍵**）

- orchestrator 如何觸及外部 planner／worker
- 外部 worker 如何觸及 orchestrator 的 callback 端點
- **一個跑在同一 compose 網路上的容器化 fake planner／worker，要如何被 orchestrator 存取？** 給出可用的位址形式
- 已知的 `host.docker.internal` 在 Docker Desktop／WSL2 下的失效問題（見 `CLAUDE.md`）
- **建議一個讓 fake 服務跑在 compose 網路內的做法**（服務定義的骨架即可，不需要寫完整檔案）

### 6. 觀測

- orchestrator 的日誌怎麼看，有哪些結構化前綴（如 `[RECOVERY]`）
- 如何 kill 與重啟 orchestrator 容器（crash 測試需要）
- kill 之後大約多久會完成 recovery（**只要時間量級，不要描述 recovery 做了什麼**）

### 7. 現有測試的執行方式

- Go 測試怎麼跑（含 `-p 1` 的理由）
- 現有的 acceptance 測試怎麼跑（**這些即將被封存，記錄的是操作方式，不是它們斷言什麼**）

### 8. 我刻意省略的事項

列出你認為屬於語意契約、因此沒有寫進來的東西。**這一節證明你有在守那條界線。**
