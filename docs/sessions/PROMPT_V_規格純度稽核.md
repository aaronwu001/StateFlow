# Claude Code Prompt V —— 規格純度稽核（獨立驗證者）

> **執行位置：** repo 內，唯讀。**本 session 不修改任何檔案。**
>
> **你的角色是對抗式驗證者。** 有另一個 agent 剛對規格檔做了一次「純度手術」——把實作指示、測試基礎設施規格、環境資訊、待辦清單從行為矩陣中移出，分散到各自正確的位置。**你的工作是查證它有沒有真的做完，以及有沒有在搬移過程中弄丟東西。**
>
> 你**不是**在檢查規格內容對不對（那是 owner 的職權）。你檢查的是**分離是否徹底、搬移是否無損**。

---

## 背景：這次手術的目標

行為矩陣（`spec/BEHAVIOR_MATRIX.md`）應該**只包含**「系統在 X 情況下必須做出 Y 這個可觀測反應」。

四類東西被移出：

| 移出的東西 | 應該去的地方 |
|---|---|
| 實作步驟（怎麼改 code、怎麼寫 migration、動工前查什麼） | `docs/sessions/PROMPT_B_*.md` |
| 測試基礎設施（測試分層、fake 的能力、CI、本機腳本） | `docs/sessions/PROMPT_A_*.md` |
| 環境資訊（平台、工具鏈、網路拓樸） | `docs/OPERATIONAL_FACTS.md` |
| 待辦（白皮書修補、未來想做的） | `docs/BACKLOG.md` |

---

## 檢查項目

### A. 純度 —— 矩陣裡還有雜質嗎

**A-1.** 逐節讀 `spec/BEHAVIOR_MATRIX.md`。**每一列都套用這個測試：能不能改寫成「系統在 X 情況下必須 Y」，且 Y 是可觀測的？** 改寫不了的就是雜質。逐條列出，並標明它屬於上表哪一類。

**A-2.** 機械掃描。以下任何一項出現在矩陣中都是雜質，貼出 `grep -n` 結果：

```bash
cd spec
grep -n "Session [0-9]\|快照\|STATE_SNAPSHOT" BEHAVIOR_MATRIX.md
grep -n "oracle\|_harness\|fake_planner\|fake_worker" BEHAVIOR_MATRIX.md
grep -n "CI\|GitHub Action\|test-all\|Makefile\|make test" BEHAVIOR_MATRIX.md
grep -n "WSL\|Docker Desktop\|host.docker.internal\|本機" BEHAVIOR_MATRIX.md
grep -n "prompt\|session 的 scope\|動工前\|實作時" BEHAVIOR_MATRIX.md
grep -n "待辦\|尚未\|未來\|建議做\|傾向不做" BEHAVIOR_MATRIX.md
```

**預期：** 只有第 0 節「這裡不寫什麼」那張對照表會命中，因為它就是在說明這些東西不在這裡。**其他任何命中都是漏網的雜質。**

**A-3.** 檢查「來源」欄。每一列的來源必須是白皮書章節（`§n`）或 M 節的裁定編號（`裁定 #n`）。**引用 session 編號、快照、prompts 檔的都是雜質。**

---

### B. 無損 —— 搬移過程有沒有弄丟東西

**這一項比 A 重要。** 手術最大的風險是「移出去之後兩邊都沒有」。

**B-1.** 取得手術前的版本（`git log --oneline -- spec/BEHAVIOR_MATRIX.md`，找到前一版），與現版做 diff。**列出所有被刪掉的內容**。

**B-2.** 對每一段被刪掉的內容，回答：它現在在哪裡？三種可能：

- **已搬到某個檔案** → 貼出目標檔案中對應的段落，證明它真的在
- **已改寫成正式的矩陣列** → 貼出那一列
- **完全消失** → 🔴 **這是需要回報的損失**，說明它原本說什麼

**B-3.** 特別確認以下幾項有沒有落地（它們原本在被刪掉的節裡）：

| 原本的內容 | 應該去哪 | 你要查證 |
|---|---|---|
| 測試分三層（黑箱／種狀態／不變量健檢）的判準 | Prompt A | 有沒有含「分層依據是能不能只用 HTTP + SQL 觸發」這條 |
| fake planner 必須記錄呼叫次數 | Prompt A | 有沒有，以及有沒有說明為什麼（C-14 的觀測手段） |
| fake worker 要能製造的五種失敗 | Prompt A | 有沒有列全 |
| CI 兩個 job 的分工 | Prompt A | 有沒有 |
| 本機一鍵腳本的要求 | Prompt A | 有沒有，且有沒有處理「本機沒裝 Go」 |
| migration 000002 的做法（up/down 都寫、不得改 000001） | Prompt B | 有沒有 |
| 動工前的實測查核 | Prompt B | 有沒有 |
| 白皮書 13 項修補待辦 | `docs/BACKLOG.md` | 逐項清點數量 |
| 未來可能做的項目 | `docs/BACKLOG.md` | 逐項清點數量 |

---

### C. 覆蓋 —— 移出的東西有沒有留下該留的行為

有些原本寫成「待辦」的東西，其實應該轉成正式的矩陣列。查證：

**C-1.** 白皮書 §18 已關閉的六個登記項（全史上界化、sweeper、`retry_after_seconds`、config 環境變數、migration、healthcheck），**它們現在的行為在矩陣裡有對應的列嗎？** 逐項找出列號，找不到的標為缺口。

**C-2.** `GET /healthz` 與 `GET /ui` 有沒有行為列？

**C-3.** 矩陣 L 節的自檢清單逐條實跑一次，貼出結果。特別是 L-7（API endpoint 覆蓋，九個路由）與 L-9（純度抽查）。

---

### D. 一致性 —— 四份文件之間有沒有互相矛盾

**D-1.** `docs/OPERATIONAL_FACTS.md` §5.4 說 `host.docker.internal` 在此環境實測**可用**，推翻了先前的「確定性失效」宣稱。查證這個更正有沒有傳播到：矩陣（應該完全不提這件事）、Prompt A（應該說明實測結果與新的選擇理由）、`CLAUDE.md`（若有提及）。**列出仍在複述舊宣稱的地方。**

**D-2.** `CLAUDE.md` 與矩陣是否有互相矛盾之處？特別檢查：`retry_after_seconds` 是否生效、retry delay 是否可設定、`planner_config` 該含哪些鍵、`GET /ui` 有沒有列在 API 表中。

**D-3.** Prompt A 與 Prompt B 有沒有指派同一件事給兩邊，或都以為對方會做？

## 硬規則

| # | 規則 |
|---|---|
| V-1 | **不修改任何檔案。** 發現問題就回報，不要順手修 |
| V-2 | 每一項發現都要貼出**檔案:行號**與原文。不接受「我覺得有問題」 |
| V-3 | 「沒問題」也要明說，並貼出你據以判斷的證據。**每一節都要有明確結論，不得跳過** |
| V-4 | 你不評價規格內容的對錯，只評價**分離是否徹底、搬移是否無損** |

---

## 報告格式

1. **A 組（純度）：** 逐條列出仍留在矩陣中的雜質，各標明應去何處。無則明說「無」並貼 grep 輸出
2. **B 組（無損）：** 被刪內容的完整清單，每一段標註「已搬至 X」「已改寫為列 Y」或「🔴 遺失」
3. **C 組（覆蓋）：** 六個已關閉登記項的對應列號；L 節自檢的實跑結果
4. **D 組（一致性）：** 四份文件之間的矛盾清單
5. **總判定：** 通過 ／ 擋下。擋下的話列出必須先修的項目
6. **你最沒把握的一項判斷是什麼，為什麼？**
